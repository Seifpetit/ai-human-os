Capability dependency rules:
- A capability is a reusable system ability that the feature consumes, not just a file list
- Examples include `multiplayer_room_creation`, `auth_session`, `payment_checkout`, `chat_message_delivery`
- If the capability is `missing` or `partial`, set `plan_action` to `establish_first`
- If the capability already exists and can be safely reused, set `plan_action` to `reuse_existing`
- `required_contracts` must name the shared contracts and authority boundaries the capability needs
- `existing_surfaces` must list concrete existing files or boundaries when they already exist, or `none`
- `prerequisite_operations` must point to concrete operation keys in this plan using `<file_path>::<operation_type>` when capability establishment is required
- consumer files must not appear before the prerequisite capability-establishment operations they depend on
- do not start a dependent feature at a client adapter, UI component, or server consumer if the underlying capability contracts are still missing
- if a feature would require guessing a server endpoint, shared payload, session owner, or authority boundary, the plan is incomplete and must establish those contracts first

Format Cross-File Contracts exactly as the template requires.
